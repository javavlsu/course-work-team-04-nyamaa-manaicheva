# Нагрузочное тестирование (k6)

Два расширенных сценария нагрузочного тестирования — клиентский и
административный, каждый по 7 модулям продукта. Тестовые данные готовятся
заранее (`00-seed-data.js`), поэтому регистрация не участвует в самой
нагрузке — за исключением одной осознанной группы в админском сценарии,
которая специально проверяет полный жизненный цикл пользователя.

## Установка k6

- macOS: `brew install k6`
- Windows: `choco install k6` (или `winget install k6`)
- Linux / другое: https://k6.io/docs/get-started/installation/

## Что тестирует каждый сценарий

**01-client-scenario.js** — одна "сессия" клиента:
1. Заметки — список (`GET /api/notes`, тот же "тяжёлый" запрос, что и раньше)
2. Заметки — деталь (`GET /api/notes/{id}`)
3. Директории — список
4. Директории — добавление/удаление заметки из директории
5. Комментарии — создание + список
6. Канбан — доска + перемещение задачи между колонками
7. Календарь — получение + события за диапазон дат

**02-admin-scenario.js** — одна "сессия", внутри которой два логина — сначала под админом из пула
(только для модулей 1–2), затем под обычным клиентом из того же пула, что и в
`01-client-scenario.js` (для модулей 4–7):
1. Пользователи — список (`GET /api/users`, нужна роль `Admin`)
2. Пользователи — полный CRUD: регистрация одноразового аккаунта, поиск его
   id, получение, обновление, удаление (нужна роль `Admin`)
3. Восстановление пароля — `forgot-password` → письмо в MailHog →
   `reset-password` (анонимные эндпоинты, не зависят от текущей сессии)
4. Вложения — загрузка файла на заметку клиента, список, удаление
5. Ревизии заметок — обновление заметки (создаёт ревизию) + список ревизий
6. Права доступа (Permission Access) — выдать право другому клиенту, список, отозвать
7. Аналитика — `GET /api/analytics`

> **Важно:** в API нет административного обхода прав на чужие заметки —
> проверка доступа смотрит на владельца или явный `PermissionAccess`, без
> исключения для роли `Admin`. Более того, эндпоинты вложений, ревизий,
> прав доступа и аналитики вообще не проверяют роль — им достаточно быть
> авторизованным владельцем/участником доступа. Поэтому модули 4–7
> админского сценария выполняются от лица обычного клиента из клиентского пула
> (того же, что и в `01-client-scenario.js`) и работают с его уже насеянными
> заметками, а не с отдельными "своими" заметками админа. Модули 1–2
> (список пользователей и CRUD над чужим аккаунтом) — единственное, что реально
> требует роли `Admin`, поэтому для них сессия логинится под админом из пула.

## Порядок запуска

1. Поднять бэкенд (`docker-compose up` и т.п.), убедиться, что он доступен
   на `http://localhost:8080`, а MailHog — на `http://localhost:8025`.

2. Один раз подготовить тестовую выборку:

   ```bash
   k6 run --vus 1 --iterations 1 00-seed-data.js
   ```

   Скрипт зарегистрирует пул клиентов с заметками, директориями, канбан-доской,
   календарём и комментариями; зарегистрирует пул админов (им заметки не
   нужны — все, что связано с заметками, админский сценарий тестирует от
   лица клиентов); заведёт отдельный аккаунт для проверки восстановления
   пароля. В конце вывода будет SQL-команда — выполните её один раз в базе:

   ```sql
   UPDATE "User" SET role = 'Admin' WHERE email LIKE 'loadtest-admin-%@example.com';
   ```

3. Прогнать клиентский сценарий:

   ```bash
   k6 run 01-client-scenario.js
   ```

4. Прогнать административный сценарий:

   ```bash
   k6 run 02-admin-scenario.js
   ```

   Если S3-хранилище для вложений не настроено (см. `.env`:
   `S3_ENDPOINT`/`S3_ACCESS_KEY`/`S3_SECRET_KEY`), отключите модуль вложений,
   иначе он будет валить прогон ошибками загрузки, не относящимися к
   тестируемой нагрузке:

   ```bash
   k6 run -e ATTACHMENTS_ENABLED=0 02-admin-scenario.js
   ```

5. Поправить узкое место в коде (например, фильтрацию/пагинацию списка
   заметок, которая сейчас происходит в памяти на уровне сервиса, а не в
   SQL-запросе).

6. Прогнать оба сценария ещё раз с теми же параметрами и сравнить метрики
   "до" и "после" (см. `load-test-report.xlsx`).

## Переменные окружения

Общие:

| Переменная | По умолчанию | Что это |
|---|---|---|
| `BASE_URL` | `http://localhost:8080` | адрес бэкенда |
| `THINK_TIME` | `3` | пауза (сек) между двумя запросами внутри "сессии" |
| `CLIENT_EMAIL_PREFIX` | `loadtest-client` | префикс email тестовых клиентов |
| `CLIENT_PASSWORD` | `LoadTest123!` | пароль тестовых клиентов (и recovery-аккаунта) |

Для `00-seed-data.js` и `01-client-scenario.js`:

| Переменная | По умолчанию | Что это |
|---|---|---|
| `CLIENT_POOL_SIZE` | `20` | сколько тестовых клиентов создавать/использовать — должно совпадать в обоих скриптах |
| `NOTES_PER_USER` | `300` | заметок на клиента (только сидер). Чем больше — тем заметнее деградация `GET /api/notes` |
| `DIRECTORIES_PER_USER` | `5` | директорий на клиента (только сидер) |
| `NOTES_PER_DIRECTORY` | `5` | сколько заметок класть в первую директорию при сидировании |
| `COMMENTS_PER_NOTE` | `5` | комментариев на первой заметке (только сидер) |
| `KANBAN_TASKS_PER_COLUMN` | `3` | задач в первой канбан-колонке (только сидер) |
| `CALENDAR_EVENTS_PER_USER` | `5` | событий календаря на клиента (только сидер) |

Для `00-seed-data.js` и `02-admin-scenario.js`:

| Переменная | По умолчанию | Что это |
|---|---|---|
| `ADMIN_EMAIL_PREFIX` | `loadtest-admin` | префикс email тестовых админов |
| `ADMIN_POOL_SIZE` | `20` | сколько тестовых админ-аккаунтов создавать/использовать — должно совпадать в обоих скриптах |
| `ADMIN_PASSWORD` | `LoadTest123!` | пароль тестовых админов |
| `CLIENT_POOL_SIZE` | `20` | также нужен здесь: модули 4–7 выполняются от лица клиента из этого пула — должно совпадать с 00-seed-data.js/01-client-scenario.js |
| `RECOVERY_EMAIL` | `loadtest-recovery@example.com` | отдельный аккаунт только для теста восстановления пароля |
| `MAILHOG_URL` | `http://localhost:8025` | адрес MailHog (письма с токеном восстановления) |
| `ATTACHMENTS_ENABLED` | `1` | `0` — отключить модуль вложений, если S3 не настроен |

Пример запуска с кастомными параметрами:

```bash
k6 run -e BASE_URL=http://localhost:8080 -e CLIENT_POOL_SIZE=30 -e THINK_TIME=5 01-client-scenario.js
```

## Что смотреть в результатах

- `checks` — процент прошедших проверок. Падение — признак того, что сервис
  не справляется.
- `http_req_duration{endpoint:...}` — раз каждый запрос помечен тегом
  `endpoint`, в сводке можно посмотреть длительность по каждому модулю
  отдельно (`notes_list`, `kanban_move`, `permission_grant` и т.д.).
- `http_req_failed` — доля запросов с ошибкой.
- В конце вывода k6 показывает, прошли ли `thresholds` (зелёным ✓ или
  красным ✗) — это индикатор "тест провален", который можно скриншотить.

## Известное узкое место

`NoteService.GetNotesByOwnerId` сейчас загружает в память **все** заметки
владельца, а фильтрацию, сортировку и постраничную разбивку делает уже в
Java-коде. При большом количестве заметок на пользователя (см.
`NOTES_PER_USER`) каждый запрос `GET /api/notes` — это O(n) операция, поэтому
именно на ней ожидается деградация под нагрузкой.
